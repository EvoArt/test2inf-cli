# Design notes

Why this program is shaped the way it is, and the measurements behind the
choices. All timings are on the real badger cohort — 3,224 badgers, 29,737
timepoints, 51 years, 58 parameters (70 with Se/Sp inferred) — unless stated.

## Gradients are analytic, not AD

The log-posterior's gradient is a hand-derived reverse sweep
(`src/grad_analytic.jl`) rather than automatic differentiation.

| gradient | time | vs analytic |
|---|---|---|
| analytic reverse sweep | **1.63 ms** | 1.0x |
| Turing/DynamicPPL + Mooncake | 6.02 ms | 3.7x |
| Turing/DynamicPPL + ForwardDiff | 29.49 ms | 18.0x |

Against a 1.37 ms primal, the analytic sweep costs 1.3x primal and Mooncake
4.4x. Textbook reverse mode is 2–3x, so the gap is tape overhead rather than
anything intrinsic: profiling puts ~33% of gradient self-time in `IdDict`
get/setindex inside Mooncake's tape, GC-flagged, with four of the top six frames
doing dynamic dispatch. The likelihood itself is 1.1% of self time.

Worth stating clearly, because it is the counter-intuitive part: **the PPL layer
is not the cost.** DynamicPPL evaluates this model within 7% of a hand-written
dependency-free kernel (1.37 ms vs 1.27 ms). Only the AD tape is slow.

The forward-mode dual implementation in `src/dual.jl` is retained as the
independent reference the test suite differentiates against — the analytic sweep
is checked against it to ~1e-14 across every model variant, both year processes
and both penalty settings.

## Two samplers

`--method nuts` adapts a diagonal metric from scratch and is always safe.

`--method hmc --model <name>` runs fixed-length HMC with a step size, trajectory
length and **dense** inverse mass matrix tuned offline per variant and compiled
in (`src/pretuned.jl`, generated by `tune/tune_hmc.jl`).

| | wall | min ESS | min ESS/s |
|---|---|---|---|
| NUTS (1000 warmup + 1000 draws) | 431 s | 679 | 1.57 |
| HMC, pre-tuned dense (1000 + 200) | **30.6 s** | 144–461 | 4.7–15.1 |

The dense metric matters because of the year process. Under `rw1`,
`gamma = sigma_g * cumsum(raw)`, so every year effect shares a factor with
`sigma_g` — a funnel, which is exactly the off-diagonal structure a diagonal
metric cannot represent. Dense samples at eps ≈0.29 against diagonal's ≈0.047,
with tree depth 4.0 against 6.3: about one sixth the gradient evaluations per
draw.

Measuring this needs care. Comparing *total* wall time (warmup + sampling) makes
dense look like a wash, because adapting a dense metric is the expensive part
(~66 gradients/iteration against 8). But adaptation is paid once, offline, which
is the entire point of shipping tuned values — so the honest denominator is
post-warmup sampling time, where dense wins by roughly 8x.

The tuned values were verified against NUTS across four seeds: worst z-score
1.99–2.53 with a different parameter on top each time, 0–12% of parameters above
|z|>2 against the ~5% expected by chance, sd ratios 0.91–1.14. That pattern is
Monte Carlo noise; a wrong stationary distribution would put the same parameter
on top every seed.

## The metric is not locked in the binary

`--metric <path>` reads an inverse mass matrix from a headerless CSV and
overrides the compiled-in one. `--write-metric <path>` exports the metric that
was used, and works under `--method nuts` too.

So tuning for a different cohort needs no rebuild and no Julia: run NUTS once
with `--write-metric`, then pass that file to `--method hmc --metric`. The
compiled-in metrics are a convenience for one dataset, not the only route.

`read_metric` is deliberately separate from `read_matrix`, which skips a header
row — silently dropping a mass matrix's first row would give either a shape
error or, worse, a plausible-looking wrong metric. `write_metric` uses
`string(::Float64)` rather than the 8-digit CSV formatter, so the round trip is
exact.

## The year process is a model choice

`--year-process rw1` (default) or `iid`:

| | rw1 | iid |
|---|---|---|
| gamma | `sigma_g * cumsum(raw)` | `sigma_g * raw` |
| sigma_g prior | `Normal+(0, 0.05)` | `Normal+(0, 0.30)` |

These are different models, not tuning options, and they do not share tuned
values — rw1 needs a step size roughly 6x smaller and a trajectory roughly 6x
longer. `PretunedHMC` therefore carries the process it was tuned under, and a
mismatch is refused.

rw1 is the default because it is what `test2infeR` defaults to, and what every
published fit in this project used. It also costs ~4.5x the wall time of iid to
sample, for the funnel reason above.

## Each badger is expanded onto the full timestep grid

A badger seen at t=10 and t=20 contributes ten transitions, not one: an
uncaptured timestep carries no emission but still advances the hazard. Supplying
only capture rows and supplying a pre-expanded grid therefore give identical
results — `build_data` expands either way.

This is worth stating because getting it wrong is quiet. On the real cohort the
difference is 14,986 transitions against 29,737, and a log density shifted by
~174 at the same parameters with the same emissions.

Prevalence is reported over badgers actually **captured** at a timestep, not
over every badger present. The `captured` flag exists for exactly that
distinction; averaging over filler grid steps biases prevalence up, because
those steps sit later in a record where infection is more likely.

## Trimming traps

`juliac --trim=safe` is unforgiving, and a clean build proves nothing — two bugs
here produced zero verifier errors and a binary that crashed at runtime.
`build.sh` therefore runs every model variant under both methods with
`JULIA_LOAD_CODEGEN_LIB=0`, so any JIT fallback fails loudly, and refuses to
declare success otherwise.

- **`Core.Box`**: assigning a result in both arms of an `if`/`else`, or
  capturing a loop-reassigned variable in a closure, boxes it and erases its
  type. One boxed variable produced 40+ verifier errors. Split into separate
  functions instead.
- **`open(path, "w") do io`** does not trim (it goes through `_apply_iterate`).
  Use explicit `open`/`try`/`finally close`.
- **Over-narrow annotations are a hazard**, opposite to the usual advice:
  `parse_int(s::String)` crashed at runtime because `strip()` returns a
  `SubString` and the conversion method had been trimmed away. Use
  `AbstractString`.
- **`ntuple(f, N)` with `N` a type parameter stops unrolling above 8** and
  allocates — chunk 12 cost 86 ms against 138 µs. Always `ntuple(f, Val(N))`.
- **Do not slim the bundle by guessing.** Two attempts failed identically:
  a hand-maintained "unused" list, and keeping exactly the executable's
  imports. The first deleted libraries Julia links into every build
  (libgmp, libmpfr, libblastrampoline, libgfortran, libopenblas64_); the
  second deleted their transitive dependencies. Both ran fine locally --
  the loader found the missing DLLs on PATH, because a developer machine
  has Julia installed -- and failed on a clean CI runner with exit 127 and
  no output at all. Correct slimming needs the full transitive closure of
  the import graph, which is a real tool rather than a shell loop.

## No cross-compilation

JuliaC builds for the host, so each platform's bundle must be built on that
platform. `.github/workflows/build-cli.yml` does this on Windows, Linux, macOS
ARM and macOS Intel runners, and attaches the bundles to a release on a `v*`
tag. Building locally can only ever produce one of them.
